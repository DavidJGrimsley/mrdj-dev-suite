# Expo React Native projects

Select `expo-react-native` explicitly for the established React Native generator. Its compatibility adapter reuses the existing `create-expo-super-stack` package; that package and existing CLI/MCP identifiers are compatibility interfaces, not Jenny's product name. User-facing actions say **Generate new Expo project**.

Keep supported choices for TypeScript/JavaScript, package manager, Expo Router or React Navigation, styling, auth, state, onboarding and legal flows, backend/data, and project memory. Do not reduce the adapter to a generic `create-expo-app` invocation or silently discard the existing options.

Resolve an immutable executable identity during planning and verify it again before execution. Preserve legacy behavior for callers using compatibility tools, while new plans bind approval to their selected version and arguments. Installing dependencies requires the reviewed plan's authorization.

Read version-specific documentation for the app's actual Expo SDK. Relevant existing MDS resources are `mds://guides/post-create-onboarding`, `mds://skills/expo-router-architecture`, `mds://skills/uniwind-theming`, `mds://skills/api-routes`, `mds://skills/deployment`, and `mds://skills/production-server-patterns`. Load only the resources needed for the selected configuration. Auth and backend integrations remain optional decisions; never infer that every app needs Supabase or accounts.

Use Expo Doctor and the project's actual scripts when verifying Expo. Keep Expo checks out of Exact verification. Preserve canonical workspace memory discovery and existing source/configuration when onboarding. Workspace initialization, repository movement and Git-worktree changes remain separate approved operations.
